# Machine-readable output

The `--json` surface is a contract with scripted consumers. Always pass `--json` and check the exit status ([exit-codes.md](exit-codes.md)).

## Rules

1. **Success writes exactly one JSON document to stdout**, carrying `schemaVersion`. This holds for every command with `--json`, including `job`, `slot`, `host`, `authored` and `prove`.
2. **Failure writes exactly one error document to stdout**, `{ "schemaVersion": 1, "error": "<human message>", "code": "<tag>" }`, then exits non-zero. `error` is the sentence the text mode would print. `code` is a stable tag consumers may branch on (`engine-missing`, `invalid-argument`, `unknown-job`, and so on).
3. **Machine mode is engaged before any output**, so every diagnostic goes to stderr and cannot interleave with the payload.
4. **stdout carries nothing else.** No banners, no progress, no warnings. `host init --json` sends its progress lines to stderr. Commands that wait on a job (`job run`, `job wait`, `job watch`, `prove`) print no step progress under `--json`.

Without `--json`, `job`, `slot`, `host` and `authored` print text meant for a person: a verdict line, a short result line, or `key: value` lines. Their text is not a contract.

`--raw` (`status --raw`) engages the same stdout discipline for a porcelain stream: rules 3 and 4 apply, rules 1 and 2 do not. `doctor` and `verify` have no `--json` mode; `check` reports `verify` as a step.

## Versioning

`schemaVersion` is `MACHINE_OUTPUT_SCHEMA_VERSION` in `src/utils/machine-output.ts`. Adding a key does not bump it. Removing or retyping a key does, with a changelog note.

## `check` verdict line

`FIREFORGE-VERDICT: PASS|FAIL [reason=step-failures|lock-timeout|skipped-steps failed=<steps>] steps=<n> skipped=<n> [skipped-steps=<steps>] [selection=narrowed]`

`skipped-steps=` appears whenever a step is skipped; `reason=skipped-steps` when `check.failOnSkipped` fails a run on an `unavailable` skip alone. `selection=narrowed` marks a run whose `--only` or `--skip` left steps out, so a PASS does not cover the full sequence.

## `test` verdict line

`FIREFORGE-VERDICT: PASS|FAIL reason=<reason> [note=<class>] [keys…]`, a single final stdout line. `log=<path>` names the run's complete output under `.fireforge/logs/` ([run-logs.md](run-logs.md)).

| Reason              | Meaning                                                                                                                                                                 |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `crash`             | The harness or browser died, or an exit-0 run showed no positive check count or no completed suite. There is no trustworthy result; retried within `--harness-retries`. |
| `server-startup`    | A mochitest server never came up before any test ran. Retried like `crash`; this is what is left once the budget is spent.                                              |
| `harness-arguments` | Profile or other harness argument setup failed before any test ran. A rebuild is not the repair.                                                                        |
| `no-tests`          | The run dispatched but nothing ran, or the summary counted zero.                                                                                                        |
| `test-failures`     | The suite ran and reported unexpected results, or requested files never started or ended.                                                                               |
| `preflight`         | The run was refused before the harness was reached. Its text is written to stdout and the run log before the verdict.                                                   |
| `inconclusive`      | A result exists, but `engine/` moved under it or a perf run changed power source, so it was discarded.                                                                  |
| `lock-timeout`      | The run never started: the engine session lock stayed contended.                                                                                                        |
| `killed`            | A signal ended the run, or FireForge ended it because its parent vanished. `signal=` names the signal or `parent-exit`.                                                 |

### `note=`

A preflight refusal that can classify itself adds `note=<class>`. Classes are not a closed set: treat an unknown one as opaque. Current values: `browser-busy`, `stale-browser`, `stale-browser-kill-failed`, `marionette-port-busy`, `mochitest-port-busy`, `coverage-replaced`, `stale-build`, `stale-components`, `stale-compiled` (compiled sources changed after the binary was linked), `no-launchable-binary`, `no-build-baseline` (no recorded build and no `--allow-stale-build`), `invalid-build-baseline` (names the first failing field), `baseline-write-failed`, `negative-control` (the control diff was refused), `negative-control-pending` (an interrupted control could not be undone safely), `control-built` (the binary still carries a compiled control whose restore build never ran or failed). `negative-control-restore` rides a `reason=inconclusive` line whose control could not be restored byte-exact.

`note=coverage-replaced` adds `build-paths=<path>,…`: the requested paths to rebuild, engine-relative with forward slashes. Within an entry `%`, `,` and whitespace are percent-encoded; split on `,` and `decodeURIComponent` each entry. A script retries with `fireforge test --build <paths>`. The key is absent when the uncovered request is the whole suite, whose remedy is `fireforge build`.

### `--results` document

`{ schemaVersion, files, unfinished, controlBaseline?, dispatches?, controls? }`. `files` and `unfinished` hold numbered runs only (`run >= 1`). A negative control's unmutated dispatch is `controlBaseline: { files, unfinished }`. `dispatches` lists exact rosters, including requested files that never started. `controls` records applied and restored mutations. A harness-level record whose `test` is `automation.py` carries `shardFiles`, plus `file` when its shard has exactly one file.

## Job verdict line

`<job-id> <state> [slot=<name>] [step=<i>/<n>] owner=<label> [host-load-peak=<n> host-load-peak-at=<s>] [host-state=<entry>@<s>,…] [host-disk-low=<GiB>@<s>] [reason=<first line>] [logs="fireforge job logs <id>"] [output=<path>]… [detached=<pid>,…] [cancelled-by="<owner> from <cwd>"] [blocked=<why>]`. `host-load-peak=` is a failed job's last step's highest one-minute load average and how many seconds into the step it was seen. `host-state=` lists what changed on the host under a failed or interrupted job's last step (`networkLost`, `lidClosed`, `displaySlept`, `input`, `foreground-lost`), each with the seconds into the step it was first seen, earliest first. `host-disk-low=` is the lowest free space, in GiB and seconds into the step, a red, interrupted or cancelled job's last step saw below the low-disk threshold. A test step's `reason=` ends with `(started=<n>/<m> first-unstarted=<path>)` when its verdict says where the run stopped. `detached=` lists processes that outlived a phase with no foothold in the slot; the slot is marked for audit.
