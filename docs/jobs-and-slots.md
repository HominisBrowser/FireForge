# Jobs and slots

In a source-mode project, `build`, `test`, `run`, `package` and `check` work run as jobs: the caller captures its checkout, a local supervisor runs the work in a private clone of the engine (a slot), and the result is one verdict line. The caller can disconnect and reconnect by job ID. `passed` means the job's steps, declared test files, cleanup and final source audit passed; whether that is enough for a change is [proof](proof.md).

Everything runs as one user. The boundary is a Unix socket inside a 0700 namespace, so nothing here authenticates people: a job's `owner` is a display label, and anyone on the host can read any job by ID. The label defaults to `<worktree>@<branch>` (`<worktree>@<short commit>` when HEAD is detached, `user@host` outside git), so sessions tell apart; `FIREFORGE_OWNER` or `--owner` sets it. `job cancel <id>` records who cancelled (owner, working directory, pid, time), which `job status` and `job list` print as `cancelled-by="<owner> from <cwd>"`; cancelling a job another owner submitted is refused unless `--force` is given. The default namespace is `~/.fireforge/host/jobs`, and `FIREFORGE_COORDINATOR` selects another. Use one namespace per host.

In a project the namespace has configured, direct `build`, `test`, `run`, `package` and `furnace` refuse outside a job, in every worktree of that repository. `status`, `lint`, `typecheck` and `verify` still run directly, from a snapshot of the checkout. `check` runs only as a job (`job run`, whose default it is, or `prove`): in an editing checkout it refuses with `authored-proof-needs-slot`.

## Set up the host

From the main checkout or any linked worktree:

```sh
fireforge host init --slots 2 --from-engine /path/to/configured/engine
```

This creates the namespace, freezes a toolchain, provisions the slots and qualifies them. It is safe to rerun: every step keeps what is already right. It never edits a project file.

- `--from-engine` needs an engine that was configured and built once (it reads `config.statusd/substs`). A source-mode project cannot run `download` or `bootstrap`, so get that engine from a legacy checkout or build one elsewhere first. Without it, `host init` sets up the coordinator and slots only, and static jobs work.
- A project made by `fireforge setup` blocks on the first run: `configs/common.mozconfig` has `--enable-bootstrap`. `host init` prints the edit (replace it with `--disable-bootstrap`), exits 1, and leaves static work usable. Make the edit and rerun.
- `--slots 0` sets up the coordinator alone. `--cpu`, `--memory`, `--max-slots`, `--browsers` and `--quiet-load` override the capacity below; `--disk-low-gib`, `--artifact-max-gib` and `--artifact-max-age-days` set the disk and artifact bounds described under Disk and artifacts. `--replicate-depth` sets when a build is replicated (see Build replication below). `--pristine-repository` names the pristine object donor; `--python` names an interpreter; `--cache` and `--release-secrets` are described below.
- A queue project is refused with the command that migrates it: `fireforge authored migrate --out <directory> --verify`.
- With `--json` stdout is one document (`namespace`, `capacity`, `maxSlots`, `quietLoad`, `slots`, `built`, `project`); progress goes to stderr, and a blocked host answers with the error envelope.

## Run work

```sh
fireforge authored override browser/themes/shared/tabs.css   # first touch of an upstream file
$EDITOR src/browser/themes/shared/tabs.css
fireforge job run --test browser/themes/test/browser_tabs.js
```

`job run` captures the checkout, submits, waits and prints one verdict line. Exit 0 is passed, 16 failed, 17 cancelled or interrupted, 18 `--timeout` ran out (the job keeps running). The job ID is on stderr as soon as it is submitted; `job wait <id>` reattaches.

While it waits, and in `job wait`, `job watch` and `prove` when they wait, stderr gets one plain line each time the job enters a step (`step 6/11 lane:tiles, running 1h04m, 1h04m in, passed 4 red 1 blocked 0`) and one when a step ends (`step 5/11 check: red`). Nothing repeats while nothing changes, a step still queued behind a `blockedBy` reason is left to the `waiting:` line for it, and steps finished before the wait began are counted in the next step line rather than listed. The lines are the same on a terminal and in a log, with no redraws. Under `--json` none are printed, so stdout stays the one document and stderr carries no progress. There is no switch to silence them.

A job that needs a built slot waits for a peer that holds one rather than building a second. `job run --test` on a host with no build refuses at submit and exits 1, naming `fireforge job run --build full` and `fireforge job run --build full --test <path>...` (both in one job); a full build takes hours on a real tree. Any other job nothing on the host can ever run is refused the same way, naming the command to run. When the build it needs exists only in a quarantined slot, the refusal names that slot, its quarantine reason and `fireforge slot restore <name>` (with `--stop-orphans` when a leftover process holds it) instead.

### Watch

```sh
fireforge job watch --test browser/themes/test/browser_tabs.js   # rebuild and retest on every save
fireforge job watch --check --build none                         # the project check on every save
```

`job watch` is the source-mode form of `watch`. It captures the checkout as it stands, submits the job `job run` would, prints that job's verdict line, and does it again whenever a save changes what a capture holds, until Ctrl-C. A capture whose snapshot is the one last submitted submits nothing, so saving a file unchanged costs a capture and no job.

- What it watches is what a capture selects: `sources.root`, `sources.metadataRoot`, `fireforge.json`, `package.json`, `package-lock.json`, `furnace.json`, `components/`, `configs/` and each `--path`. Files Git ignores (unless `--path` names the file itself), editor temporaries (swap, backup and lock files) and the rest of the checkout, `engine/` included, never start a capture. Watchman watches each selected directory when it is installed and answers; otherwise Node's recursive `fs.watch` does (FSEvents on macOS, ReadDirectoryChangesW on Windows, one inotify watch per directory on Linux, bounded by `fs.inotify.max_user_watches`). The first line on stderr names which.
- A capture starts once changes have been quiet for `--debounce <ms>` (default 500). However many saves come in meanwhile, they are one pending capture.
- A change while a job runs supersedes it by default: the job is cancelled through `job cancel`, its `cancelled` verdict line printed, and the newer snapshot submitted, so the latest edit wins. A save that leaves the snapshot as it was cancels nothing. With `--no-supersede` the running job finishes, then one capture takes whatever changed meanwhile.
- `--slot <name>` names a slot. With the default `auto` the scheduler picks the first job's slot and every later job names it, so its object directory stays warm.
- `--build ui|full|none` (default `ui`), `--test <path>...`, `--check`, `--headed`, `--repeat <n>`, `--shuffle <seed>`, `--path <path>...`, `--owner`, `--allow-dirty-root` and `--namespace` mean what they mean for `job run`. `--headed`, `--repeat` and `--shuffle` need `--test`; `--build none` needs `--test` or `--check`.
- Stdout carries one verdict line per finished job, as `job run` prints it, or under `--json` one job record per line. A red one is followed on stderr by its red step and `fireforge job logs <id>`, which opens on that step. Submissions, waits and refusals go to stderr; a refused capture or submission (a dirty file outside the capture, say) leaves the watch waiting for the next change.
- Ctrl-C or SIGTERM cancels the job in flight through `job cancel` and waits up to 60 seconds for the cancel to settle; a second one stops at once, and the cancel stands. The exit code is the one `job run` gives the last job that ran to its own end: 0 when it passed or when none did, 16 failed, 17 cancelled by someone else or interrupted. A job the watch cancelled itself, for a newer capture or for the stop, does not count.

Watch jobs are ordinary jobs. Each request is the one `job run` with the same flags submits, naming the kept slot as `--slot` would, with nothing in it about watching; a passed watch job is evidence as a `job run` one is.

### Interactive run

```sh
fireforge job run --run                                      # build what changed, open the browser
fireforge job run --run --profile ~/fireforge-profiles/dev   # the same, keeping the profile between runs
fireforge job run --run --build none -- about:config         # no build; arguments for the browser after --
```

`job run --run` builds what changed (a UI build unless `--build` says otherwise), opens the browser from a slot and stays attached: the job's output, the browser's console included, streams to the terminal under a `--- step <n>: <command>` heading per step, and the verdict line comes last once the window closes. Under `--json` the output goes to stderr and stdout is the job's record. Ctrl-C or SIGTERM cancels the job through `job cancel`, so the slot is settled and audited as after any cancel, and the command exits 17; a second one stops waiting at once, and the cancel stands. The run holds the display like a `--headed` test, with a keep-awake assertion unless `--no-keep-awake`, and its step's deadline is 12 hours.

Each run starts from a fresh temporary profile unless `--profile <dir>` names one to keep. That directory must be absolute; it is created if missing. It is refused inside a slot, inside the coordinator namespace, or inside the checkout's tracked source (a path the checkout's Git ignores is fine). Browser arguments never name a profile: `-P`, `-profile` and the profile manager are refused, and so is `--profile` on any other run step, such as a gate's `runs`.

A person drives the window, so an interactive run is never evidence: `prove` takes nothing from a job that holds one, kept profile or not, and its steps hold no obligation's place while it runs. Each run is new work, never a repeat of an earlier one.

`job submit request.json --snapshot snapshot.json` runs anything `job run` does not express (`fireforge authored capture --out snapshot.json` makes the snapshot). `job status`, `job wait`, `job logs`, `job list`, `job cancel <id>` reconnect by ID, or by a prefix of it of at least 8 hex characters that names one job; an ambiguous prefix is refused, listing the IDs it matches. None of the reads starts a supervisor. `job logs` reads bounded chunks (`--offset`, `--limit` up to 1048576 bytes). `--step <n>` reads one step's output, numbered from 0 as in `artifacts/<job>/step-<n>-*`, with offsets counted from its start; a step that ran again after a requeue shows its latest run. Asked for no range, a failed job's log opens on its red step (the last red one when it went on past reds), or that step's last chunk when it is longer, with a note on stderr naming the step and how to read the others; a red step that wrote nothing shows the log from its start. `job status` and `job wait` exit nonzero for failed, cancelled and interrupted jobs. While a job is under way, its record carries `progress`: the current `step` (from 0) of `steps`, its `label` (prove's obligation ID, a request step's `label`, or its command and arguments), whether it is `running` or waiting, `stepStartedAt` and `stepSeconds` while it runs, `startedAt` and `elapsedSeconds` since its first step was admitted, and `results`, each earlier step's `label` and `state` (`passed`, `red` or `blocked`). `job status` and `job list` print it as `progress="step 6/11 lane:tiles, running 12m05s, 1h04m in, passed 4 red 1 blocked 0"`.

A request is its steps; everything else has a default:

```json
{ "steps": [{ "command": "test", "args": ["--headless", "browser/foo/browser_x.js"] }] }
```

`sourceId` comes from `--snapshot`. `key` defaults to a digest of the request: a repeat attaches to the live or passed job and runs anew after a failure. An explicit `key` is strict. `slot` is optional. A test or run step may set `env` and `uploadDir`, any step `keepAwake`, a step may set `label` (up to 120 printable characters, the name progress shows, part of nothing it proves), and a step may set `deadlineSeconds` (default: full build 6 hours, other builds and tests 2 hours, an interactive run 12 hours, anything else 1 hour). A run step with `"interactive": true` is one a person drives, as `job run --run` writes it: it is a job's last step, may carry `profile` (an absolute directory, with the rules above), and is never evidence.

## Output

Default output is human text. `--json` writes exactly one JSON document with `schemaVersion` (a job as its record, `job list` as `{jobs}`, `slot list` as `{slots}`), and failures as `{schemaVersion, error, code}`. Whole-number flags (`--cpu`, `--timeout`, `--slots` ...) that are not whole numbers are usage errors: exit 8, code `invalid-argument`. Refusals carry `unknown-job`, `ambiguous-job`, `unknown-slot`, `invalid-log-range`, `job-cannot-run` and `executor-mismatch`, each with the next command in its text. In a queue project, `job run`, `prove`, `slot create|prepare|refresh-deps`, `host init` and the `authored` source commands say to run `fireforge authored migrate --out <directory> --verify`.

## Capacity

Defaults come from the host: every available CPU, 80% of physical memory in GiB, three slots, one browser, one display. A build claims 75% of the CPU budget (or the project's `build.jobs` if lower) and half the memory, and that figure is its `-j`. A step that names its own concurrency claims exactly that: `--jobs <n>` or `--jobs=<n>` on a build, check or test step, and `-j <n>` or `-j<n>` on a build. The value is read once at submit and is what the job reserves and what the command runs with. Given more than once, in any spelling, above the host's CPU, or above 1 on a test step, the request is refused at submit. A static phase claims 2 CPU and 2 GiB, a browser test 2 CPU and 4 GiB. `--browsers <n>` lets more browsers run at once once you have measured that they can; windows stay one at a time.

A job that cannot start reserves what it waits for, and a later job passes it only if it fits and touches nothing reserved. Every queued job reports why in `blockedBy`: the resource, a quarantined slot (with the restore command), the host, the disk or the display. A step with a window waits for the host's one display, whichever slot it would run on, and says who has it: `blockedBy: Waiting for the display, held by job <id> step <n>`. It also waits with `blockedBy: display: <reason>` while no display is active: graphics off, every display asleep, or a closed lid with no external display. A closed lid with an external display counts as active, and an unreadable display counts as available.

Quiet applies per step. Only a lane, stress, run, check or control that declares `quiet` is quiet, and a control always is; the job's other steps are admitted like any other work. A request that sets `quiet` itself, rather than on its steps, makes every step that does not say otherwise quiet and exclusive.

A quiet step is either exclusive or shared:

| Quiet step                                                                      | What may run beside it                                                                                                                    |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| exclusive: a test with `--perf-samples`, or any step of a request-level `quiet` | nothing                                                                                                                                   |
| shared: every other quiet step                                                  | a static check (`check`, `typecheck`, `lint`, `verify` or `status` that is not quiet itself and claims no build, browser or display lane) |

A static check starts beside a shared quiet step only while the host's one-minute load, plus the CPU it claims and the CPU already admitted beside the step in the same pass, stays under the quiet limit; an unreadable load starts none. Everything else waits with `blockedBy: Waiting for the quiet phase of job <id> (step <n>/<m> <label>, holding the host for <time>); only a static check runs beside it`. The load guard below still judges the quiet step, so a red under load from what ran beside it is no verdict on the step.

A quiet step waits for what cannot run beside it to finish (`blockedBy: Draining the host for this quiet phase: waiting for job <id>`); an exclusive one waits for everything, a shared one also for room beside the static checks still running. Then it waits for the host's one-minute load, which counts every process on the host and not only jobs, to fall below the quiet limit: `host init --quiet-load <n>`, by default the CPU capacity. Meanwhile it reports `blockedBy: host-load: one-minute load <x> is at or above the quiet limit <n>`, and every job behind it waits too, static checks included, so a stream of them cannot starve it. Each step queues with a fresh ticket once the one before it ends, so when a quiet step finishes, the host is released: jobs that waited during it go ahead of the job's next step, which then drains the host again. A quiet phase still waiting when its step deadline has passed since it queued ends `interrupted`, since nothing ran. A quiet step that goes red while its load peak, less the CPU the step was admitted with, reached the limit also ends `interrupted` (exit 17), with no verdict against the step and its reason naming the peak; the next `prove` runs it again. A pass under load stands. A check stays parallel when every `check.extraSteps` entry declares `"footprint": { "static": true }` (optionally with `cpu` and `memory`): it then claims up to a quarter of the host and needs no toolchain. A step without a footprint may do anything, so that check needs a quiet host and the native toolchain.

A test needs a roster: `expected.files` or test files named as arguments. Each file must start and finish in the harness results; a file that did not is a red.

## Host conditions

A test or run step watches the host on the same 30-second tick as its load peak, and records what changed under it in its evidence as `hostState`, each entry the seconds into the step it was first seen:

| Entry            | Seen when                                                                                   | Read on             |
| ---------------- | ------------------------------------------------------------------------------------------- | ------------------- |
| `networkLost`    | no interface other than loopback or a tunnel keeps an address beyond link-local             | every platform      |
| `lidClosed`      | the lid closes                                                                              | macOS               |
| `displaySlept`   | no display stays active: graphics off, every display asleep, or a closed lid alone          | macOS               |
| `input`          | keyboard or pointer input reaches the host (`HIDIdleTime` is shorter than the step has run) | macOS, window steps |
| `foregroundLost` | another application is frontmost while the step's own browser runs                          | macOS, window steps |

Network, lid and display count only once a sample saw them fine, so a step that starts offline or with the lid closed is not excused by it. A red step ends `interrupted` (exit 17) instead, with no verdict against it and its reason naming what changed, when the network went away under any step, the lid closed or the display slept under a quiet step, or input reached a step with a window. The next `prove` runs it again. A pass stands. A red or interrupted job carries its last step's `hostState`, and each red in `stepVerdicts` carries its own; `--json` shows them. `hostState` is context only: no fingerprint, identity or proof reads it.

A step with a window also reads which application is in front. Every two seconds, and at the start, the executor asks `lsappinfo` for the frontmost application's process and compares it with the browser the step started from its slot, which needs no permission prompt and sends no Apple Event. A host that will not say, or a browser not started yet, reads as unknown, never as a loss. `foregroundLost` (spelled `foreground-lost` in a verdict line) records the seconds into the step when another application was first in front; a capture taken from then on may show that application instead of the browser. It annotates only: a red under it stays red. `--hold-front` raises the browser again, and the annotation stays. Other platforms hold the display lease and report the foreground as unknown.

A harness reads the lease and the foreground through the step's environment: `FIREFORGE_DISPLAY_LEASE` is `<job>:<step>` while the step holds the display, and `FIREFORGE_DISPLAY_STATE` names a JSON file, `{lease: {job, step}, foreground: "own" | "other" | "unknown", since}`, rewritten whenever the foreground changes. Both are set for a window step on a real host only.

## Disk and artifacts

Every step samples free space on the namespace's volume, and on the slot's when that is another volume, on the same tick as its load peak. A volume is low below `host init --disk-low-gib <n>` GiB (default 10) or 3% of the volume, whichever is larger. A step whose free space fell below that records the lowest reading as `hostDisk` (`freeBytes`, `atSeconds`, `volume`). A failed, interrupted or cancelled job carries it, its verdict line shows `host-disk-low=<GiB>@<seconds>`, and its reason gains a sentence that the red may come from disk pressure, with what the coordinator holds in slots (the sizes their builds were measured at) and in job artifacts. The state of the job does not change. `hostDisk` is context only, as `hostState` is.

`fireforge host status` prints free space on the namespace's volume against that threshold, what slots and artifacts hold, and a warning when free space is low. Under `--json` it writes `{namespace, disk: {freeBytes, totalBytes, lowBelowBytes, low}, slots, slotBytes, artifactBytes}`.

Job artifacts (`artifacts/<job>/`, including each step's output directory) are bounded by size and age: `host init --artifact-max-gib <n>` (default 10) and `--artifact-max-age-days <n>` (default 14). Only a finished job's artifacts are ever removed, never a queued or running job's, and never those of the newest three finished jobs of each owner. A finished job past the age bound goes first; then, while artifacts exceed the size bound, the oldest of the rest. A directory no job names goes once a day old. A supervisor prunes when it starts and, while it stays up with no work, once an hour. `fireforge host prune` does the same on demand, prints each job it removed with its reason (`age`, `size` or `orphan`) and what it freed, and takes `--max-gib` and `--max-age-days` for one run and `--dry-run` to remove nothing. Under `--json` it writes `{namespace, dryRun, removed: [{id, bytes, reason}], freedBytes, remainingBytes}`.

## Slots

Each pin has one pristine template in the namespace. A slot is a clone of it (`cp -c -R -p`, a physical copy where the volume has no copy-on-write) and takes minutes.

```sh
fireforge slot create b                          # from this checkout
fireforge slot create c --from a                 # clone a built slot, objects included
fireforge slot list | audit <name> | prepare <name> --snapshot s.json | remove <name> | restore <name>
```

- `slot create` works from any checkout and takes only the new slot's lock. `--pristine-repository` is needed only if the pin has no template and the checkout has no `engine/`.
- `slot create` then qualifies the new slot's native sites, as `host init` does, when the host has a frozen toolchain and the source's mozconfigs disable bootstrap; a qualification that goes red fails the command, naming `slot qualify-native <name>`. When it cannot qualify, or `--no-qualify` says not to, it warns on stderr that native jobs refuse on the slot, says why and names `slot qualify-native <name>`.
- `--from <built-slot>` clones source and objdir together, so an incremental build sees only real differences. If this host's toolchain built the source slot, its UI-build anchor comes along (the anchor records which compiled inputs the build holds); otherwise the next build is full. Qualifying the clone relocates its object directory.
- Build replication: when jobs queue for the one slot holding the build they need while another slot sits idle, the supervisor copies that build into the idle slot so both serve. It acts when the holder is between jobs, before it takes the next one, and at least `--replicate-depth` jobs (default 2) wait per slot that holds the build; `host init --replicate-depth 0` turns it off. Only a build a UI build extends is replicated: a job that only reads a package keeps waiting for the slot that built it, since a copied package still names that slot's paths. The destination is an idle slot on the same pin that no queued job names, could start on, or needs the build of; one with no build is taken first, then one that needs a full build anyway. Holding both slots' locks, the supervisor clones the source's engine, Git metadata, captured root, dependency trees and object directories beside the destination (copy-on-write, so minutes and little disk) and swaps them in; the destination keeps its Mach sites and private state, takes the source's anchor, source and recipe at a generation past both slots', and needs a build before its package is trusted. Without copy-on-write it replicates only while free disk above the floor exceeds twice the source's measured object directory. A `qualify-native` job, owned by `fireforge replication`, then relocates the copied object directory; until it passes, the destination takes no other job. Meanwhile waiting jobs report `blockedBy: Waiting while replicating slot a's build into b, so more than one slot can serve this job` and `slot list` shows `replicating="slot a's build into b: <copying|swapping|relocating>"`. A source that does not audit, a host whose toolchain did not build it, or a slot a process holds leaves both slots untouched. A relocation that does not pass, or one a supervisor restart interrupts, leaves the destination without the copied objects and `needs=full-build`. A restart during the copy leaves the destination as it was; one during the swap leaves it `needs=full-build` and quarantined, for `slot restore`. The source is never quarantined by a replication.
- `slot remove` works under the slot's lock in any state and refuses while a process holds a file in the slot.
- Dependency trees: a slot holds the root `node_modules` plus whatever `slots.dependencyCaches` declares as `{source, target, lockfile?}`. `source` is relative to the checkout; one under `engine/` comes from the engine `--from-engine` names; `--cache <target>=<path>` names another place on this host. A `target` is a canonical path that names nothing a slot's runtime owns; inside `engine/` it can only be a `node_modules` that upstream does not track. A tree with npm's install record (`.package-lock.json`) is compared with an npm lockfile, whatever its directory is called, and refused if they disagree. A `node_modules` with no record is refused. Any other tree cannot be compared: `slot refresh-deps`, `slot create` and `host init` say so, and the slot identifies it by its bytes and its lockfile by its digest, so a moved lockfile over the same bytes draws a warning rather than a refusal. A tree holding private state, an absolute link or a link leaving the tree is refused. Every tree a slot is given is also kept in `<namespace>/dependency-trees/`, by target and lockfile digest, the four most recently used per target. A job whose lockfile is not the one its slot's tree was installed for takes the stored tree for its own lockfile into the slot before it runs, after checking it lands as the bytes that were stored, so checkouts on different lockfiles share slots and one checkout's `slot refresh-deps` does not break another's queued jobs. A job whose lockfile no slot was ever given refuses and names `fireforge slot refresh-deps <name>...`, which replaces the trees from this checkout and deletes nothing outside their targets. It reads only `fireforge.json` and the declared lockfiles, which must be committed; other uncommitted paths are taken at their committed bytes. Trees follow lockfiles rather than the pin, so it serves slots on another pin than the checkout's; a lockfile the pin itself holds (an engine lockfile the source does not own) is read at the slot's pin, and a tree that disagrees with it is refused.
- Storage: a slot's reservation is what its object directory can still grow to (the largest built slot's size, or five times the source until one exists), checked with the other slots' growth and an 8 GiB free-disk floor. A job waits for room rather than failing. A release build has a second object directory, which is refused at submit unless the disk has room for it above the floor; what the slot's release directory held at its last release counts as already there.

## Failures and recovery

A red step, a refusal before launch and a cancel with a clean process census end the job and return the slot to the pool; the next job there audits it first. A request with `continueOnFailure` (which `prove --tier gate` sets) goes on past a plain red instead: the slot is audited as the next job would audit it, and the job runs its next step. A step that reads the package or builds over the anchor is blocked, not run, when the last build before it went red or was blocked, or when the package could not be vouched for after a red. A step that cannot be settled cleanly or a failed audit still ends the job. The job ends `failed`, its `stepVerdicts` list each red and blocked step, its reason starts `<n> of <m> steps red`, and every step that passed is sealed as evidence. A slot is quarantined only for uncertainty: a process that cannot be shown to be gone, a failed audit, an unrestored negative control, an interrupted or over-30-minute preparation or seal, or a supervisor interrupted while holding it. Jobs waiting on it stay queued and `blockedBy` names it.

- `fireforge slot restore <name>` re-materializes the slot from the template plus its snapshot, keeps its object directory (and declared dependency trees), audits, and clears the quarantine. It refuses while a process uses the slot, naming it. `--stop-orphans` first stops the holders that are orphans: a process whose parent is init, or one with no running job and no interactive shell among its ancestors, found by its working directory, an open file under the slot or a command line naming it. It sends SIGTERM, waits, then SIGKILL, and prints each pid stopped with its command; it never stops a running job's process, a supervisor or an interactive shell's descendant, and refuses by name while any other holder remains. When every holder is an orphan the plain refusal names the flag. The next build must be full. Safe to repeat.
- `slot audit` reports integrity and clears nothing. Do not delete locks or quarantine files by hand.
- A process group that outlives its phase holds its slot until it is gone. A self-detached descendant whose command line names the slot is stopped with the phase. That includes one no sample saw as a descendant but which carries the phase's environment marker, such as the xpcshell harness's `moz-http2.js` server, which runs in a session of its own and outlives a harness that exits without stopping it. Any other self-detached descendant, sampled or marked, with no foothold in the slot is reported as `detached=<pids>` on the verdict and the slot is audited next; one holding the slot open quarantines it. The slot remembers each reported process by its exact birth, in `detached.json` beside its metadata, at most 32 of them, newest kept; a clone or replica of the slot starts without that record. Every later admission audit, and `fireforge slot audit`, looks at each one again: one that has exited, or whose pid now belongs to another process, is forgotten; one still without a foothold stays remembered; one that now has a working directory or open file under the slot, or a command line naming it, quarantines the slot with a reason naming the process, its command, the job that left it and what it holds (`process <pid> (<command>) left detached by job <id>, now holds <path>`). Once its job has ended such a process is an orphan by the rules above, so `slot restore --stop-orphans` stops it, and `slot restore` forgets the record. A marked process that appears only after the phase's processes were stopped quarantines it too. A process with a working directory or open file in a slot is found at seal and at admission, so an editor or shell sitting in a slot quarantines it.
- Host-wide quarantine (an executor whose start could not be established) shows in `blockedBy` on every job. `fireforge job host-clear` clears it once a process census succeeds; `--forget-group <group>` clears a group whose number now belongs to something else.
- One damaged journal row moves to `journal.damaged.jsonl`; that job ends `interrupted` and the host keeps running. A supervisor that cannot start says why to the client that started it (`supervisor.log`). Terminal jobs older than 30 days leave the journal with their logs.

A red's reason carries the step's last complaint, and a test step's stopping point (`started=<n>/<m> first-unstarted=<path>`) when its verdict has one. A failed job's verdict line names its last step's load peak (`host-load-peak=`), and a failed or interrupted job's names what changed on the host under that step (`host-state=networkLost@12,input@40`), and low disk (`host-disk-low=<GiB>@<s>`). An executor killed from outside ends the job `interrupted` (exit 17) with no verdict against its step.

## Builds and the package

A build advances a slot's identity only when it succeeds. UI-only source changes keep the compiled anchor; C++, Rust, build-manifest or `configs/` changes need a full build. A build that can touch compiled output clears the anchor before it launches, so a failed one leaves nothing a later source could match. Changed tools need `mach clobber objdir --full` and a full build.

A build records a stat signature of its package (`dist/bin` and any `dist/*.app`, minus lock, update, crash and log files), and of the file each symbolic link in it resolves to inside the objdir or outside the slot (such as a toolchain library under `~/.mozbuild`), so a target that changes moves the signature without the link changing. A link into the engine's source tree is left to the slot's source audit, which binds it to the captured snapshot. A step that reads the package checks it before launch and every seal checks it again; a package that moved costs the slot its anchor (and `slot audit` reports it), so the next build is full. A harness that writes elsewhere under `dist/` costs a full build per test job, so watch the refusal's named paths.

`run` always uses a fresh temporary profile (`--profile` refuses). `--profile-file` and `--console-allow-file` take only captured files.

`job run --release` submits `package --recipe release`. It needs `build.release` in the config: `overlay` (a captured mozconfig fragment appended last), optionally `secrets: {variable, files}`, and optionally `outputs`. `variable` is set to the directory that `fireforge host init --release-secrets <dir>` recorded, and a missing file refuses at submit. It builds in `.fireforge/release/obj` in the slot, emptied first so every release is built from clean, with the frozen tools and one build date, leaving the development build untouched. `outputs` lists paths in that object directory (`dist/*.app`, `dist/*.dmg`, `dist/host/bin/mar`, `config.status`; `*` only in the last segment), and each is copied to the step's output directory at the same relative path, a clone where the volume supports one. A declared output the build did not produce reads red. The output directory (`output=` on the verdict, kept 30 days with the job's artifacts) holds those copies and `release.json`, the build's identity. Package checks, signing and notarization are the project's, run against those copies.

## Toolchain

The toolchain belongs to the host. `host init --from-engine` reads the engine's `config.statusd/substs`, runs nothing but Python, and clones each tool read-only under `~/.fireforge/toolchains/<digest>/` (`FIREFORGE_TOOLCHAINS` moves the store). The digest covers bytes, relative paths and platform, so hosts with the same tools agree. System and Xcode paths are used in place; so is a Python that could not be cloned (a Homebrew build), or name one with `--python`. `WASI_SYSROOT`, `MACOS_SDK_DIR` and the ONNX Runtime directory (`FIREFORGE_ONNX_RUNTIME_DIR`, turned into `--with-onnx-runtime` by the generated mozconfig) come along; a slot whose configure loses or changes one is refused at qualification.

Identity is checked by stat signature per job and by bytes at derivation, qualification and a request's `finalGate`. Quality tools (FireForge, ESLint, Prettier, Node) are recorded in receipts and cache keys and do not bind the compiled anchor.

Captured mozconfigs must set `--disable-bootstrap`; a native step on one that does not is refused at submit naming the file, line and edit. `slot qualify-native <name>` (which `host init` runs per slot) provisions the Mach sites at the slot's final path and runs `mach configure` with the frozen tools. The sites are `mach`, `common` and `build`, plus `taskgraph` when the source declares `build.release`: `mach package` resolves its DMG tools through `mach taskgraph`, which provisions that site with hash-pinned pip from PyPI, as the build site is. A native step runs only on the recorded sites: a site Mach adds that nobody qualified reads red by name, and a source whose roster differs from the slot's record (a release declared after the slot qualified) is refused before it runs, naming `slot qualify-native <name>`. Qualification provisions afresh any site it did not record and removes a recorded one the source no longer needs.

Installed dependency trees are read by stat signature and re-read when it moves. A slot has no repository, so a project check that needs the tracked file list reads `$FIREFORGE_CAPTURED_FILES`, one path per line.

## Environment

| Variable                        | Effect                                                              |
| ------------------------------- | ------------------------------------------------------------------- |
| `FIREFORGE_COORDINATOR`         | Namespace; default `~/.fireforge/host/jobs`.                        |
| `FIREFORGE_TOOLCHAINS`          | Toolchain store; default `~/.fireforge/toolchains`.                 |
| `FIREFORGE_OWNER`               | Owner label shown by `job list`, in place of `<worktree>@<branch>`. |
| `FIREFORGE_PRISTINE_REPOSITORY` | Pristine donor, ahead of the template and the checkout's `engine/`. |

Jobs do not inherit a caller's environment: `PATH`, `HOME`, locale and display cross from the values recorded when the coordinator was set up, and steps declare anything else. The supervisor is a detached child of the first client that needs one, and inherits that client's login session and macOS privacy grants. A first client that is sandboxed or on SSH passes those limits to every job until the supervisor exits: a step with a window then refuses at submit, and a supervisor that cannot read FireForge's own folder is stopped and named by `Coordinator did not start`.

One coordinator runs one FireForge.

- Pinned build: `fireforge host upgrade [--from <package directory>]` copies a built FireForge package (its `dist/`, `runtime/`, `templates/`, `package.json` and production dependencies, without tests or source maps) into `<namespace>/runtime/<id>/`, checks that the copied dependencies resolve to the same packages, runs the copy under the coordinator's Node to record its executor fingerprint, and records it as current in one rename. `--from` defaults to the package running the command; a checkout needs `npm run build` first. From then on every supervisor start runs the pinned build, whichever checkout or worktree starts it, after checking every byte of it against the record; a pinned build that is missing or changed stops the start with `Coordinator could not start` and the `host upgrade` remedy. `host upgrade --previous` returns to the build pinned before; the namespace keeps those two, plus any build a running supervisor still runs from. `host status` shows the pinned and previous builds, the build the running supervisor runs, and whether this checkout is the pinned build. With `--json`, `host upgrade` writes `{namespace, pinned, previous}` and `host status` adds `runtime: {pinned, previous, supervisor, client}`.
- Clients on a pinned host: a checkout of another build submits normally. The pinned build runs and seals every job, and `prove` measures evidence against the pinned build, so results read the same from every checkout. `job run`, `prove` and other submitters print one notice line when this checkout is not the pinned build. What a client must share with the host is the coordinator protocol (the socket requests, job request, authored snapshot and job view); a client speaking another protocol than the pinned build is refused with exit 1 and code `executor-mismatch`, naming both builds and `fireforge host upgrade`.
- Switching builds: after `host upgrade` while a supervisor of another build runs, that supervisor finishes what it was running and accepts new jobs for the pinned build without running them: they stay `queued` with `blockedBy: Waiting for the host to switch to FireForge <version>, which it does once the running supervisor goes idle`. Once only such jobs remain it goes idle (`idleMs`, 30 s by default), closes and starts the pinned build, which runs them. A running supervisor that records no protocol, or another one, refuses submissions with `executor-mismatch` until it goes idle.
- Without a pinned build, the supervisor runs from the package of the client that started it. A submit from a client whose FireForge differs (`npm ci` in one worktree only, or a rebuilt checkout) is refused before anything runs, with exit 1 and code `executor-mismatch`: results sealed by the other FireForge would read as stale for this one. The refusal names the supervisor's package and version. Give the checkouts the same install (the same `package-lock.json`, then `npm ci` in each) and let the supervisor go idle, or pin one build with `host upgrade`.

`job status`, `job wait`, `job logs`, `job list` and `job cancel` work across builds, as do `prove status` and `prove plan`, which submit nothing.
